# UI Korean / i18n Plan

Status: Draft  
Owner: UI  
Date: 2026-04-01  
Branch: `feat/ui-i18n-ko`

## Summary

Add a lightweight i18n layer to the Paperclip UI and ship Korean as the first additional locale.

Recommendation:

- do not hard-code Korean directly into components
- keep English as the source locale and fallback
- introduce Korean as `ko`
- keep route paths, API values, IDs, and user-generated content unchanged

This gives a maintainable path for Korean now and additional locales later without forcing a full i18n framework migration up front.

## Goals

1. Make the core Paperclip UI available in Korean.
2. Add a minimal multilingual foundation that supports at least `en` and `ko`.
3. Keep existing behavior, routing, and API contracts stable.
4. Make future upstream rebases manageable by localizing through a small set of utilities and message files.

## Non-Goals

- translating URL paths like `/agents` or `/projects`
- translating server enums, API payload keys, or database values
- translating user-authored issue/project/goal content
- introducing a large i18n dependency unless the lightweight approach proves insufficient
- full localization of every screen in the first pass

## Recommended Product Shape

### 1. Lightweight in-repo i18n layer

Add a small typed message system inside `ui/src` instead of introducing `react-intl` or `i18next` immediately.

Recommended files:

- `ui/src/i18n/messages/en.ts`
- `ui/src/i18n/messages/ko.ts`
- `ui/src/i18n/index.ts`
- `ui/src/i18n/LocaleProvider.tsx`
- `ui/src/i18n/useT.ts`

Recommended behavior:

- source locale: `en`
- supported locales: `en`, `ko`
- fallback: `en`
- locale resolution order:
  1. explicit persisted selection in `localStorage`
  2. browser locale if supported
  3. `en`

### 2. Keep phase 1 simple

Phase 1 should localize copy, labels, buttons, empty states, and onboarding text.

Recommendation:

- no translated route paths
- no server-driven locale storage in v1
- no pluralization engine beyond simple helper formatting unless required by real copy

### 3. Add locale state at the app root

The provider should be mounted at the root UI entry:

- `ui/src/main.tsx`

It should expose:

- current locale
- `setLocale(locale)`
- `t(key, params?)`

### 4. Update document language metadata

Also update:

- `ui/index.html`

The `lang` attribute should reflect the active locale when possible. Static default can remain `en`, but runtime should update `document.documentElement.lang`.

## Implementation Notes

### Message key strategy

Recommendation:

- use semantic keys, not English sentence keys
- namespace by screen or component

Examples:

- `nav.dashboard`
- `nav.projects`
- `onboarding.start`
- `agents.empty.title`
- `approvals.pending.title`

This keeps rename churn low and reduces merge conflict noise.

### Interpolation

Support basic named interpolation:

- `t("onboarding.addAgentToCompany", { companyName })`

This is enough for the current UI copy patterns in `App.tsx` and the main detail pages.

### Formatting

If date or number formatting needs localization, use browser `Intl` directly instead of embedding formatting logic in the translation layer.

## Technical Milestones

1. Add the locale provider and typed message dictionaries.
2. Wire the provider into `ui/src/main.tsx`.
3. Replace hard-coded copy in app shell and onboarding flows with `t(...)`.
4. Translate core board pages.
5. Add a basic locale switch entry point.

Recommendation for locale switch:

- v1: a small selector in instance settings
- optional short-term fallback: `localStorage` only during development

## Release / Local Usage Path

Once the UI work is ready:

1. build `ui/dist`
2. copy it into `server/ui-dist` via `scripts/prepare-server-ui-dist.sh`
3. either run Paperclip from the source repo or replace the installed package's `server/ui-dist`

The server already prefers `server/ui-dist` for static serving and uses `ui/` directly in dev middleware mode, so this plan fits the current project structure without server routing changes.

## Risks

- the UI currently has a large amount of inline copy spread across many files
- detail pages and dialogs will likely contain more strings than the app shell suggests
- upstream rebases may touch the same files frequently, especially navigation and onboarding

Mitigations:

- centralize translation lookups early
- localize shared shell components first
- keep the first pass focused on high-traffic screens

## Recommendation

Implement this as multilingual infrastructure plus Korean locale support, not as a one-off Korean patch.

That gives the best balance of:

- immediate Korean usability
- maintainability
- lower rebase pain
- cleaner path to future locales
